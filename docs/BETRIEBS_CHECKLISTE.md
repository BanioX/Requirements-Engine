# Betriebs-Checkliste (Teilaufgabe 5 — 10 Punkte)

> **Abdeckung:** Alle 6 geforderten Bereiche (*Daten, Sicherheit, Betrieb, Deployment, Infrastruktur, Organisatorisches*) mit je 4 relevanten Punkten (24 Punkte total).
> **Status-Legende:** `umgesetzt` (wie umgesetzt), `geplant` (konkret wie?), `bewusst weggelassen` (begründet warum?).
> **Abgleich:** Alle Einträge stimmen 1:1 mit der tatsächlichen Umsetzung von **Requirements Engine** überein.

| Bereich | Punkt | Status | Wie / warum |
| :--- | :--- | :--- | :--- |
| **Daten** | Persistente Speicherung über Container-Neustarts | **umgesetzt** | PostgreSQL 17 nutzt das benannte Docker-Volume `pg_data` (`/var/lib/postgresql/data`); Schema-Initialisierung beim Start ist idempotent (`CREATE TABLE IF NOT EXISTS` + `app_meta`-Flag). |
| **Daten** | Automatisierte Datenbank-Backups & Restore-Test | **geplant** | Täglicher `pg_dump`-Cronjob (komprimiert) auf ein separates Netzlaufwerk oder verschlüsselten Cloud-Speicher; monatlicher Restore-Test in einen isolierten Test-Container. |
| **Daten** | Datenexport & Vermeidung von Vendor Lock-in | **umgesetzt** | Integrierte 1-Klick-Exporte für Management-Report (A4-PDF), Backlog inkl. realer Zeiten (UTF-8 CSV für Excel), Jira-Import (REST API v3 / Markup / Jira-CSV) sowie Einzel-Spezifikationen (Markdown). |
| **Daten** | Replikation / Hochverfügbarkeits-Cluster (Multi-Node DB) | **bewusst weggelassen** | Einzellaptop-Demo ohne 24/7-SLA; eine PostgreSQL-Instanz mit Volume genügt. Für den produktiven KMU-Betrieb wäre eine verwaltete Datenbank mit Stand-by-Replikat sinnvoll. |
| **Sicherheit** | Secrets strikt ausserhalb des Repositories | **umgesetzt** | DB-Passwort liegt ausschliesslich in lokaler `.env` (per `.gitignore` und `.cursorignore` gesperrt); `.env.example` enthält nur Platzhalter; GitHub Actions prüft die komplette Git-History automatisch mit Gitleaks. |
| **Sicherheit** | Transportverschlüsselung (HTTPS / TLS) & keine offenen Ports | **umgesetzt** | Cloudflare Tunnel (`cloudflared`) baut eine verschlüsselte ausgehende Verbindung auf; TLS-Terminierung erfolgt an der Cloudflare-Edge, sodass am Laptop/Router keine Firewall-Ports geöffnet werden müssen. |
| **Sicherheit** | Container-Härtung, Input-Validierung & Rate-Limiting | **umgesetzt** | App-Container läuft als Non-Root (`USER node`, Node 24 Alpine); `helmet` setzt strikte CSP-Header (inkl. opt-in `EMBED_ALLOWED_ORIGINS` für Confluence-Einbettung); ID-, Längen- und JSON-Validierung liefern sauber HTTP `400`; Write-Rate-Limiter schützt vor Spam. |
| **Sicherheit** | Benutzer-Authentifizierung & Rollenrechte (Admin / Nutzer) | **geplant** | Rollen-Trennung (*Nutzer* vs. *Admin/Chef* für Report, Excel-Export & Kommentar-Sichtbarkeit) ist im Backend vorbereitet und optional per `MANAGER_PIN` in `.env` aktivierbar; für den produktiven Firmeneinsatz folgt ein vollwertiger Admin-Login bzw. SSO (Entra ID / Cloudflare Access Zero Trust). |
| **Betrieb** | Aktiver Healthcheck & DB-Pool Auto-Reconnect | **umgesetzt** | Endpunkt `GET /health` führt `SELECT 1` gegen PostgreSQL aus (HTTP `200` / `503`); Docker-Healthchecks für `app` und `db` sowie `depends_on: condition: service_healthy`; `pg`-Pool-Error-Handler verhindert Prozessabstürze bei kurzzeitigem DB-Ausfall. |
| **Betrieb** | Automatische Container-Neustarts bei Absturz | **umgesetzt** | Alle produktiven Services in `docker-compose.yml` nutzen `restart: unless-stopped`, sodass ein abgestürzter Prozess selbstständig neu gestartet wird. |
| **Betrieb** | Zentrales Log-Management & Monitoring mit Alarmierung (z. B. Prometheus/Grafana) | **bewusst weggelassen** | Für den lokalen Demo-Betrieb auf dem Laptop genügen Docker-Logs (`docker compose logs`) und der aktive `/health`-Endpunkt. Ein zentraler Monitoring-Stack würde unnötig RAM/CPU binden. |
| **Betrieb** | Rückmelde- und Wiedervorlage-Kontrolle (Closed Feedback Loop) | **umgesetzt** | Nach-Ablehnungs-Zähler (`post_decision_mentions`), Entscheid-Zufriedenheitsvoting (`👍/👎`), 90-Tage-Rückmeldehinweis für CRM-Ref-IDs und revisionssicheres `decision_log`. |
| **Deployment** | Automatisierte Tests & Build-Pipeline (CI) | **umgesetzt** | GitHub Actions führt bei jedem Pull Request und Push auf `main` automatisierte Unit- & API-Tests (`npm test`) sowie den Gitleaks-Secret-Scan aus; erst bei grünem Ergebnis wird das Docker-Image gebaut. |
| **Deployment** | Multi-Arch-Container-Image & feste Release-Versionen | **umgesetzt** | GitHub Actions baut `linux/amd64` und `linux/arm64` via Buildx/QEMU und pusht nach `ghcr.io/baniox/requirements-engine` (`latest`, `sha-...`, `v1.0.0`). So startet das Image auf ARM64- und x86_64-Geräten ohne Anpassung. |
| **Deployment** | Automatisiertes Pull-Deployment auf lokalem Host (CD) | **umgesetzt** | Watchtower (`nickfedor/watchtower`) prüft alle 30 Sekunden per Label-Filter (`com.centurylinklabs.watchtower.enable=true`) die Registry und aktualisiert nur den App-Container ohne Handarbeit und ohne DB-Unterbruch. |
| **Deployment** | Getrennte Staging-Umgebung & Blue/Green-Deployment | **geplant** | Im echten KMU-Betrieb automatisches Deployment von `develop` auf eine Staging-Instanz, automatisierte E2E-Tests und erst danach kontrollierter Rollout auf Produktion (Blue/Green oder Rolling Update). |
| **Infrastruktur** | Reproduzierbare Infrastruktur als Code (IaC) | **umgesetzt** | Gesamter Stack (App, DB, Volume, Cloudflare Tunnel, Watchtower) ist deklarativ in `docker-compose.yml` und `Dockerfile` definiert und vollständig versioniert. |
| **Infrastruktur** | Dedizierter Server / Cloud-Hosting (24/7-Betrieb) | **geplant** | Migration des unveränderten Compose-Stacks auf eine Linux-VM (z. B. Schweizer Cloud-Provider oder On-Premises-Server) mit fester Custom Domain und Named Cloudflare Tunnel statt Quick Tunnel. |
| **Infrastruktur** | Horizontale Skalierung & Load Balancer | **bewusst weggelassen** | Zielgruppe sind KMU-Teams mit tiefer bis mittlerer Last; ein einzelner Node.js-Container verarbeitet hunderte Anfragen pro Sekunde. Ein Load Balancer wäre Over-Engineering. |
| **Infrastruktur** | Ressourcen-Limits (CPU/RAM-Quotas) & Festplatten-Überwachung | **geplant** | In Produktion `deploy.resources.limits` pro Container definieren und Host-Disk-Warnung ab 80 % Belegung einrichten, damit das PostgreSQL-Volume nie vollläuft. |
| **Organisatorisches** | Klare Verantwortlichkeiten & Dokumentation (Runbook) | **umgesetzt** | `README.md`, `docs/ARCHITEKTUR.md` und `AGENTS.md` dokumentieren Zweck, Start, Tests, Betrieb und Spielregeln eindeutig; im Produkt selbst sind pro Prozess verantwortliche Rollen hinterlegt. |
| **Organisatorisches** | Nachvollziehbare Änderungs- & Freigabeprozesse (Git-Workflow) | **umgesetzt** | Keine direkte Entwicklung auf `main`: Feature-Branches (`feat/...`), Pull Requests, automatische Checks und bewusste Freigabe durch den Betriebsverantwortlichen; automatische Dependency-PRs via Dependabot. |
| **Organisatorisches** | Datenschutz & Verzicht auf echte Personendaten | **umgesetzt** | Ausschliesslich anonymisierte Demodaten im Repository; keine Kunden- oder Mitarbeiter-Personendaten gespeichert. Für den Echtbetrieb ist eine Datenschutzerklärung & Löschkonzept gemäss revDSG vorgesehen (**geplant**). |
| **Organisatorisches** | Notfall- & Wiederanlaufplan (Disaster Recovery / SLA) | **bewusst weggelassen** | Für eine benotete Schul-Demo ohne produktive Geschäftsabhängigkeit ist ein formelles SLA-/Pikettdienst-Konzept unverhältnismässig; im produktiven Einsatz zwingend mit RTO/RPO festzulegen. |
